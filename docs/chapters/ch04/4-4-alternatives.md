# 4.4 错误处理的替代方案

错误处理是所有现实软件中的重大问题，因此自然存在多种途径。若检测到错误且无法在函数内部局部处理，该函数必须以某种方式把问题传达给某个调用者。抛出异常是 C++ 为此提供的最通用机制。

有些语言把异常设计成只是返回值的另一种机制。C++ 不是这样的语言：异常被设计用来报告未能完成给定任务。异常与构造函数和析构函数集成在一起，为错误处理和资源管理提供一致的框架（[§5.2.2](../ch05/5-2-concrete-types.md#5.2.2)、[§6.3](../ch06/6-3-resource-mgmt.md)）。编译器经过优化，使返回一个值远比把同一个值作为异常抛出更便宜。

抛出异常并非报告无法局部处理之错误的唯一方式。函数可以通过以下方式表明它无法完成所分派的任务：

- 抛出异常
- 以某种方式返回一个指示失败的值
- 终止程序（通过调用诸如 `terminate()`、`exit()` 或 `abort()` 之类的函数；[§16.8](../ch16/16-8-program-exit.md)）

我们在下列情况下返回错误指示（“错误码”）：

- 失败是正常且预期的。例如，打开文件的请求失败很常见（也许没有那个名字的文件，或者无法以所请求的权限打开）。
- 直接调用者可以合理地被预期去处理该失败。
- 错误发生在一组并行任务之一中，而我们需要知道是哪个任务失败了。
- 系统内存极少，异常的运行时支持会挤占关键功能。

我们在下列情况下抛出异常：

- 错误如此罕见，以至于程序员很可能忘记检查。例如，你上一次检查 `printf()` 的返回值是什么时候？
- 错误无法由直接调用者处理，而必须沿调用链向上渗漏到某个“最终调用者”。例如，让应用中的每个函数都可靠地处理每一次分配失败和网络中断，是不现实的。
- 反复检查错误码会冗长、昂贵且易错。对错误的测试以及把错误码当作返回值传递，很容易掩盖函数的主逻辑。
- 可以在应用的较低模块中加入新的错误种类，而较高层模块并未编写为应对这类错误。例如，原先单线程的应用改为使用多线程，或资源被放到远程并通过网络访问。
- 没有合适的错误码返回路径。例如，构造函数没有可供“调用者”检查的返回值。特别是，构造函数可能为多个局部变量调用，或在部分构造的复杂对象中调用，基于错误码的清理会相当复杂。类似地，运算符通常也没有明显的错误码返回路径。例如，`a*b+c/d`。
- 函数的返回路径因需要同时传回一个值和一个错误指示而变得更复杂或更昂贵（例如一个 `pair`；[§15.3.3](../ch15/15-3-containers.md#15.3.3)），可能导致使用输出参数、非局部错误状态指示器或其他变通办法。
- 从错误中恢复依赖于若干次函数调用的结果，从而导致需要在调用之间维护局部状态以及复杂的控制结构。
- 发现错误的函数是一个回调（函数实参），因而直接调用者甚至可能不知道调用了哪个函数。
- 错误意味着需要某种“撤销动作”（[§5.2.2](../ch05/5-2-concrete-types.md#5.2.2)）。

我们在下列情况下终止：

- 错误属于无法恢复的一类。例如，对许多——但并非全部——系统而言，没有从内存耗尽中合理恢复的办法。
- 系统的错误处理基于：一旦检测到非平凡错误，就重启线程、进程或计算机。

确保终止的一种方式是给函数加上 `noexcept`（[§4.5.3](4-5-assertions.md#4.5.3)），使得该函数实现中任何地方的 `throw` 都会变成 `terminate()`。注意，有些应用不能接受无条件终止，因此必须使用替代方案。供通用用途的库绝不应无条件地终止。

遗憾的是，这些条件并不总是逻辑上互不相交、易于应用。程序的规模与复杂度很重要。有时随着应用演化，权衡也会改变。需要经验。拿不准时，优先选择异常，因为它们的用法扩展性更好，也不需要外部工具来检查是否所有错误都得到了处理。

不要相信“所有错误码都坏”或“所有异常都坏”；两者都有明确用途。此外，也不要相信“异常处理很慢”的神话；它往往比正确处理复杂或罕见错误条件、以及反复测试错误码更快。

RAII（[§5.2.2](../ch05/5-2-concrete-types.md#5.2.2)、[§6.3](../ch06/6-3-resource-mgmt.md)）对于用异常进行简单而高效的错误处理至关重要。充斥着 `try` 块的代码，往往只是反映了为错误码设想的错误处理策略中最糟糕的那些方面。
